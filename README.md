# mxApi (MODX 3)

Единая точка входа публичного API для MODX Revolution 3: транспорт,
аутентификация, реестр эндпоинтов и их каталог. Сами эндпоинты поставляют
провайдеры — ядро mxApi, сторонние пакеты или код конкретного сайта.

MODX 2-линия живёт отдельно: [`apps/mxapi2`](../mxapi2). Каталоги
`core/components/mxapi/src/Core/`, `src/Endpoint/` и `tests/` в обоих
репозиториях **дословно одинаковы** — ядро не знает про `modX` и работает через
платформенный адаптер, различаются только реализации `src/Platform/`, модели,
загрузка и админка. Правку ядра переносить между линиями `diff`-ом, а не
переписыванием.

План развития — [`ROADMAP.md`](ROADMAP.md).

Документация для пользователей пакета — `core/components/mxapi/docs/readme.txt`
(едет в transport) и публичная дока https://docs.modx.pro/components/mxapi.
Markdown внутри компонента не держим: в transport его никто не читает, а копия
текста расходится с оригиналом молча.

## Структура

```
assets/components/mxapi/        публичная точка входа (index.php), коннектор, ассеты
    js/mgr/                     исходники Vue-приложений админки
    js/mgr/vue-dist/            собранные бандлы — коммитятся и едут в пакет
core/components/mxapi/          ← этот каталог целиком уезжает в transport
    composer.json               PSR-4 MxApi\ → src/, зависимость nikic/fast-route
    vendor/                     рантайм-зависимости; коммитятся и едут в пакет
    bootstrap.php               регистрация модели и сервиса mxapi в $modx->services
    src/Core/                   платформо-независимое ядро (общее с mxapi2)
    src/Platform/Modx3/         всё, что знает про MODX 3 и xPDO 3
    src/Model/                  модели xPDO 3 (генерируются из schema/)
    src/Endpoint/               встроенные эндпоинты (auth, meta)
    src/Processors/Mgr/         процессоры админки
    src/Manager/                подключение Vue-бандлов и лексикона
    controllers/, templates/    CMP
    elements/plugins/           плагин вкладки на странице пользователя
package_builder/packages/mxapi/ конфиг сборки transport (elements, resolvers)
composer.json, phpunit.xml      инструменты разработки — в пакет НЕ едут
tests/                          тесты ядра — в пакет НЕ едут
```

⚠️ Сборщик копирует `core/components/mxapi/` **целиком**. Поэтому phpunit и
тесты вынесены в корень репозитория: всё, что лежит внутри каталога компонента,
уедет клиентам вместе с пакетом.

## Зависимости

Две независимые установки composer:

```bash
# Рантайм пакета: только nikic/fast-route, коммитится, едет в transport
cd core/components/mxapi && composer install --no-dev

# Инструменты разработки: phpunit, не коммитится, в пакет не едет
composer install    # в корне репозитория
```

Пакетный `vendor/` **обязан** быть в репозитории и в transport: точка входа
подключает его в бутстрапе, и без него API отвечает `not_installed`.

Интерфейс админки берёт Vue 3, Pinia и PrimeVue из пакета **VueTools** через
браузерный import map — свой стек пакет не бандлит. Без VueTools на сайте API
работает полностью, а страницы админки показывают сообщение о недостающем
пакете (объявить транспорт-зависимость сборщик пока не умеет).

## Тесты

```bash
vendor/bin/phpunit    # в корне репозитория
```

Тесты гоняют ядро на `FakePlatform`, без поднятия MODX. Если для теста ядра
понадобился живой MODX — значит граница платформенного адаптера протекла.

## Сборка

```bash
# 1. Фронтенд админки (Vite; externals — vue/pinia/primevue/@vuetools)
cd assets/components/mxapi && npm install && npx vite build

# 2. Модели из схемы — только если правилась schema/mxapi.mysql.schema.xml
modxapp schema mxapi

# 3. Transport-пакет; собирается ЛОКАЛЬНО, стенд не нужен
modxapp build mxapi --no-check
```

`--no-check` обязателен: иначе сборщик запускает интерактивный визард php-cs-fixer.
Готовый zip появляется в `core/packages/` и не коммитится (см. `.gitignore`).
Версия задаётся в `package_builder/packages/mxapi/config.php`.

⚠️ `namespace_prefix` в конфиге сборки чувствителен к регистру: без него
генератор моделей кладёт классы в `src/MxApi/Model/` вместо `src/Model/`.

Стенд для установки и проверок — `modx3.art-sites.ru` (MODX 3.2, PHP 8.2).

## Данные

| Таблица | Что хранит |
|---|---|
| `modx_mxapi_client` | клиенты интеграций; секрет — только хэшем, привязка к MODX-пользователю |
| `modx_mxapi_token` | выданные bearer-токены; в базе только sha256-хэш |
| `modx_mxapi_log` | журнал вызовов: клиент, пользователь, маршрут, контекст, статус, длительность |

Имена таблиц совпадают с линией MODX 2 — данные интеграций и аудит переезжают с
сайта на двойке как есть. Все даты — unix timestamp: их пишет и читает PHP,
поэтому таймзона MySQL ни на что не влияет.

Таблицы при удалении пакета не дропаются — в них боевые учётки и аудит.

## Маршруты

Публичный префикс по умолчанию — `/mxapi/v1` (настройка `mxapi.route_prefix`).

```nginx
location ^~ /mxapi/ {
    try_files $uri /assets/components/mxapi/index.php$is_args$args;
}
```

Apache — в корневом `.htaccess` **выше** правил MODX, иначе запрос перехватит сам
MODX:

```apache
RewriteEngine On
RewriteRule ^mxapi/ - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]
RewriteRule ^mxapi/(.*)$ assets/components/mxapi/index.php [QSA,L]
```

Первое правило нужно потому, что при mod_php и CGI Apache не передаёт заголовок
`Authorization` — bearer-токен теряется, и API отвечает `token_required` на верный
токен. `Request::collectHeaders()` подхватывает его из `REDIRECT_HTTP_AUTHORIZATION`;
альтернатива — `CGIPassAuth On` (Apache 2.4.13+).

Без правки конфигурации веб-сервера тот же API доступен как
`/assets/components/mxapi/index.php?route=/auth/token` — удобно для проверки
установки, но публичным контрактом считается префикс.

## Контексты

Точка входа поднимает MODX в контексте `mxapi.context` (по умолчанию `mgr`), а
каждый эндпоинт объявляет, где он обязан выполняться (`modx_context` в
метаданных). Ядро переключает контекст **до** проверки права эндпоинта: права
процессоров принадлежат политике контекста, поэтому проверка в одном контексте с
исполнением в другом — это дыра.

| Что | Где задаётся |
|---|---|
| Контекст по умолчанию | настройка `mxapi.context` |
| Контекст эндпоинта | `modx_context` в его метаданных |
| Контекст из запроса | заголовок `X-MxApi-Context` при `mxapi.allow_request_context = 1` |
| Что разрешено клиенту | поле `contexts` в `modx_mxapi_client` (пусто — только контекст по умолчанию, `*` — любой) |

⚠️ `modAccessibleObject::checkPolicy()` (MODX 3: `modAccessibleObject.php:252`)
проверяет политику только при инициализированной сессии, иначе возвращает `true`.
Поэтому платформенный адаптер поднимает сессию сам и **отказывает**, если
состояние сессии проверку не допускает (CLI, отправленные заголовки).

⚠️ `modX::switchContext()` при инициализированном MODX сбрасывает
`$modx->user` (`modX.php:2610`), поэтому после переключения контекста адаптер
привязывает пользователя запроса заново — иначе процессор выполнялся бы от
анонима, причём молча.

## Каталог и OpenAPI

`GET /meta/endpoints` и `GET /meta/openapi` собираются из живого реестра. Служебные
эндпоинты (`context = internal`) не отдаются никогда, остальное зависит от
настройки `mxapi.catalog_filter`:

| Режим | Что видно |
|---|---|
| `all` (по умолчанию) | весь публичный контракт сайта — каталог работает как документация |
| `scope` | только то, что можно вызвать предъявленным токеном |
| `permission` | только то, на что у пользователя есть право MODX |

Ужесточать имеет смысл там, где на сайте живут несколько независимых интеграций:
при `all` клиент одной видит состав эндпоинтов другой вместе с именами прав.

## Права

Проверка идёт штатным механизмом MODX по namespace `mxapi`. Пакет создаёт шаблон
политики `mxapiTemplate`, права `mxapi_*` и политику `mxapiDefault`, но **не
назначает** её группам — доступ выдаётся вручную через Access Controls.

⚠️ В любой политике для namespace `mxapi` обязано быть право `load`: MODX требует
его при загрузке самого объекта namespace, до проверки прав эндпоинта. Без него
non-sudo пользователь получает 403 при полностью корректных остальных правах.
